## 3. 当前代码的处理链与限制

### 3.1 write 阶段的实际顺序

```text
读取原始最细层高斯及 detect / samples / model 结果
    ↓
voted：删除已归属到 accepted 水体的原水候选点
    ↓
carved：根据水体足迹、水位和逐点证据做体积清理
    ↓
合并 voted 与 carved 的删除索引
    ↓
denoise：对剩余原始高斯做连通簇 / SOR / 半径滤波
    ↓
生成新水面高斯
    ↓
写回最细层叶节点，更新必要的清单信息
```

这有两个实际影响：

1. 现有水体清理本来就可以逐点删除，水点与其他物体相连并不会自动阻止 `voted` 或 `carved`。粘连残留应检查它为什么没有进入这些删除集合。
2. 当前通用去噪发生在生成新水面之前。新水面覆盖到物体的问题，不能期待这一次去噪来修复。

对应代码：[原水删除入口](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/apply_write.cpp:1183)、[体积清理入口](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/apply_write.cpp:1213)、[通用去噪调用](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/apply_write.cpp:1434)、[生成水面尺度](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/apply_write.cpp:1532)。

### 3.2 连通簇规则

当前关键保留条件为：

```cpp
if (size[root] >= static_cast<std::size_t>(config.denoise_min_points) || border.count(root))
{
    continue;
}
```

代码位置：[apply_write.cpp](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/apply_write.cpp:623)。

其含义是：中心距离不超过 `denoise_radius` 的点通过邻接关系形成连通簇，只删除点数小于阈值且不触及块边界保护区的簇。当前边界保护检查 XY 距离，保护带为 `2 × radius`，默认约 `1 m`。

该规则没有使用离地高度、到真实主体的距离、语义可信度或原始照片证据。它适合清除很小的孤立噪点，但会保留内部密集的漂浮团；任何与大型真实物体连接的错误点，也可能随大簇保留。

## 4. 问题 A 的解决方案：独立漂浮簇

### 4.1 已确认 6 簇的局部修复

这是一条可以与通用算法开发分开实施的路径，目标仅为已核查的样本：

1. 将当前输出叶文件的 SHA-256、相对 URI 和 313 条原始记录绑定为修复输入。
2. 生成精确删除清单，按记录及出现次数匹配；存在重复记录时再结合原始叶索引消除歧义。
3. 写入单独的修复输出，只修改涉及的最细层叶文件和必要的清单元数据。
4. 检查目标记录残留数为 0，其他有效记录保持一致；新增水面记录不受影响。
5. 用截图对应视角和邻近视角验证视觉结果。删除这 313 点不等于承诺截图内所有残留或全场景漂浮物都已清除。

这条路径无需重新估计水位或重新生成整个水面，也不应使用一个粗略 XYZ 框删除区域内所有点。当前仅描述方案，尚未执行删除。

### 4.2 通用修复：簇大小作为特征，增加主体与观测判断

建议保留现有小簇滤波作为基础步骤，同时为较大但孤立的簇增加候选检查：

| 检查项 | 计算内容 | 用途与限制 |
| --- | --- | --- |
| 完整连通分量 | 簇点数、空间尺寸、跨叶归属 | 避免按单个 BIN 截断一个簇 |
| 主体关系 | 到附近可靠表面的距离、支撑方向、邻近结构连续性 | 主体需要可靠几何或观测支持，不能简单等同于“最大簇” |
| 局部尺度 | 邻域间距、簇物理尺寸、高斯尺寸分布 | 固定点数对不同采样密度的含义不同 |
| 高斯覆盖 | 中心之外的有效椭球覆盖，是否有异常拉长或跨越间隙 | 连通图可继续用中心构建，但物理接触判断不能只看中心 |
| 独立观测 | 原始图像中的物体支持、天空 / 背景矛盾、可靠多视角几何 | 渲染结果自身不能作为独立真值；没有观测属于未知 |
| 边界上下文 | 邻块中的延续结构和可信主体 | 避免把跨块树枝、建筑边缘误判成悬空物 |

建议使用明确的三种决策：

```text
保留：有可靠物体支持或可信几何延续
删除：存在强错误证据，且缺乏可信物体支持
待核查：证据缺失、遮挡严重或不同来源冲突
```

“没有拍到”“距离地面较高”“属于树木类”“簇比较小”都不应单独触发新增规则的删除。树冠、电线、桥梁等真实结构可能具备其中一些特征。

对于不同采样密度，候选范围宜参考局部点间距、物理尺寸和投影影响；阈值需由样本标定。当前不设定未经验证的全局高度或距离阈值。

### 4.3 为什么不直接把 30 改成 100，或只换 SOR / radius

在原输入与其他条件不变的情况下，100 的阈值会覆盖本次 36～72 点的 6 簇，但同样会扩大对正常小结构的删除范围，仍不能处理更大的漂浮簇。

SOR 和半径滤波依赖局部邻域统计。内部很密的错误簇可能具备正常的邻域密度；连接在大物体上的错误点也可能拥有很多邻居。因此这两种方法可以参与候选判断，不宜作为同时解决 A、B 的唯一替代方案。这里是依据判定机制的分析，尚未对赤水进行新的 SOR / radius 对照实验。

## 5. 问题 B 的解决方案：与物体粘连的原始水点

### 5.1 先定位遗漏环节

对一个确认的粘连区域，应逐点或按可解释子区域输出以下信息：

| 环节 | 必查信息 | 可能发现的原因 |
| --- | --- | --- |
| 数据来源 | 原始点还是新增水面点；所属块、叶 URI、记录索引 | 先区分 B 与 C |
| detect | 水 / 非水投票、有效观察数量、渲染水份额、几何水份额 | 未成为水候选、观察不足、混合证据 |
| samples / model | `source_water_id`、水体是否 accepted、冲突情况 | 水候选没有归属到可处理水体 |
| 足迹 | 是否在原足迹、腐蚀内部、岸边可达区 | 范围不覆盖、腐蚀排除了边缘 |
| 水位 | 对应水体高度、点的相对水位高度 | 超过某个清理分支的高度范围 |
| 保护 | `land`、`on_land`、岸线锚点分别是否命中 | 清理候选被保护条件撤销 |
| 最终动作 | 是否进入 voted / carved；保留的具体原因 | 区分“未成为候选”与“成为候选后被保护” |

目前这些是检查路径，**尚未有具体粘连样本证明是哪条路径导致残留**。不应先取消全部保护或扩大所有水体范围。

### 5.2 完善逐点水体归属与可见证据

现有 `detect` 已同时使用几何投影和渲染贡献。建议在此基础上保留足够证据，避免只凭一个压缩后的比例决定删除或保护：

1. 为候选点保留有效可见视角数、水支持数、可靠非水支持数和遮挡 / 未知数量。
2. 明确区分“投影落在图像内”和“点对该视角有实际可见贡献”。被遮挡的物体不应因其投影落入水掩码而被删除。
3. 每个视角的证据做适当归一化，避免一个大投影面积视角支配总分；相邻且几乎相同的照片不应被当成大量独立证据。
4. 同时检查水体 ID、足迹和水位可信度。邻近多个水体且归属不明时保留待核查，不能随意分给最近水面。
5. 将高斯的投影覆盖和实际贡献纳入判定。中心落在水里，不代表覆盖的所有内容都属于水；中心在物体附近，也不代表它一定是合法物体。

当前输出的 `carve_evidence.npz` 包含水份额、几何水份额和陆地索引，但该文件没有保留逐视角的完整判断过程。[证据导出代码](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/detect.cpp:720)

如果新判定需要的计数或逐视角信息无法从现有产物恢复，就只对相关块补算证据；不能声称仅改一个 write 阈值便能得到此前没有保存的信息。

### 5.3 逐点删除与真实物体保护

建议决策按以下含义实现，具体阈值通过样本确定：

| 点的证据 | 建议动作 |
| --- | --- |
| 明确属于 accepted 水体的旧水点，且替换水面覆盖该位置 | 删除原点，保留或生成替换水面 |
| 多个有效视角支持水体，同时具有异常水位 / 错误几何证据，且没有可靠物体支持 | 作为水体伪影候选逐点清理；记录依据 |
| 原图和可靠几何明确支持树干、桥墩、岸坡等真实结构 | 保留，即使位于水体上方或与水点相连 |
| 只有水面 XY 投影关系，没有可靠可见证据 | 不据此直接删除 |
| 水 / 非水证据明显冲突，或观察不足 | 标记待核查，优先补证据 |

原水替换与异常高处水点是不同分支：贴近正确水位的旧水点也可能需要替换；高于水位的点则不一定是错误点，桥梁、树枝等需要正常保留。

对 `on_land` 一类保护，应从“某个聚合比例直接否决”演进为“可靠非水观测与结构证据支持保留”，同时保留对真实岸线和物体的保护能力。新旧规则的差异必须在逐点诊断中可见。

### 5.4 弱连接的处理边界

部分错误点可能通过少量高斯与真实物体连接。必要时可以在候选区域内评估连接两侧的水体归属、语义、形状和空间连续性，对连接赋予不同可信度。

这样做的目的是区分连接两侧的点，不是删除整个大簇。单纯剪掉细连接也不可靠：真实细枝、电线、栏杆同样可能表现为弱连接。因此建议先完善逐点水证据；只有剩余样本表明确实需要时，再引入局部连接分割。

## 6. 问题 C 的解决方案：新水面覆盖到其他物体

### 6.1 现有代码与待验证风险

现有采样过程已经使用水体足迹及距离场安排采样大小，不能描述为“完全没有水体边界处理”。[足迹采样代码](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/apply_write.cpp:251)

在生成高斯时，水平尺度又综合了近邻距离和采样覆盖要求，之后使用 `Domain::horizontal_clearance` 限制尺度。[尺度计算](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/apply_write.cpp:1550)

需要注意，当前 `horizontal_clearance` 的实现计算的是到工程 XY 包围盒边界的距离，不是到每一处内部岸线或物体边界的距离。[实现](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/project.cpp:213)

因此，若具体样本被确认是新增水面记录，应检查最终尺度是否让其有效覆盖越过水体内部边界。这是代码层面的检查方向，尚未确认它就是用户所说“粘连”的实际原因。

### 6.2 约束最终覆盖，而不只约束中心位置

建议在最终尺度确定后检查：

- 高斯中心属于正确水体，且不在可信非水障碍物占据区。
- 最终高斯的水平有效覆盖范围落在允许的水体范围内。
- 对近岸、狭窄水道和物体附近单独细化，水体内部继续使用较大的高斯。
- 缩小尺度导致覆盖不足时，局部增加或拆分水面采样，避免产生裂缝。

若采用椭球的某个 `kσ` 轮廓作为有效覆盖近似，应显式定义 `k` 和允许的渲染尾部误差。高斯没有严格有限支撑，不能把一个有限轮廓说成绝对零溢出边界。

对当前水平轴对齐水面，可以先用保守的覆盖边界检查；对于斜岸、凹角和狭窄区域，需检查轮廓或多个边界采样点，不能只看两个轴向距离。

修复这类问题可能需要重新生成少量边界水面点，但可复用已确认的水体模型和水位，不必重新运行全场补水。只有足迹本身错误时，才补算受影响区域的足迹。

## 7. 如何接入代码及复用现有结果

### 7.1 建议的代码调整位置

| 模块 | 建议调整 | 说明 |
| --- | --- | --- |
| `detect.cpp` / `gpu.cu` | 可见性、独立视角支持与水 / 非水证据；候选诊断输出 | 已有证据可复用；缺失信息按块补算 |
| `apply_write.cpp` 中的水体清理 | 为逐点清理增加明确原因，细化保护判定和水体归属检查 | 保持逐点处理，不依赖整个簇是否与物体相连 |
| `apply_write.cpp` 中的通用去噪 | 增加独立簇候选特征、主体关系与证据判定 | 不仅调整 `denoise_min_points` |
| 水面采样与生成逻辑 | 对最终覆盖范围做岸线 / 障碍物检查，必要时局部重采样 | 仅在 C 类样本成立时实施相应修改 |
| `types.hpp` / 命令行解析 | 新规则开关、仅诊断模式、版本化参数 | 新增名称属于后续设计，不是现有可运行参数 |
| `lod.cpp` 及叶节点写入 | 复用标准写入、点数、包围盒和空叶节点处理 | 粗层 BIN 内容保持不变 |

复杂的新判断宜拆成可独立验证的函数或模块，再由 write 调用；不把所有规则继续堆叠在一个长条件表达式里。

### 7.2 两种执行方式

**方式一：在现有处理结果上做局部补充清理。**

适合已确认 6 簇、少量粘连点和局部边界水面问题。输入为当前处理后的最细层数据，输出另存。能复用的水体高度、足迹和相机信息继续使用；如需额外可见证据，仅对候选区域补算。

**方式二：修改 write / 相关判定后，从匹配的原始输入重写受影响块。**

适合将新规则正式接入后续流程。只有原始输入、模型和中间证据匹配时，才能复用 detect、reconcile、samples 等产物。若修改了水体归属或足迹，应根据依赖关系重算对应后续阶段，不能直接沿用失效结果。

### 7.3 索引、来源与数据一致性

原始 detect 的点索引指向原始最细层输入。处理后的 LOD 已删除旧点并追加水点，不能把旧索引直接套到输出文件上，即使该索引仍未越界也可能指向错误记录。

建议实施以下约束：

1. 证据记录输入文件摘要、叶 URI 和原始点索引，使用前核对身份。
2. 对现有结果修复，建立原始点到输出点的映射，或在当前结果上重新计算局部证据。
3. 原始记录未改变时可用记录字节匹配，但必须处理重复记录及数量，不能仅把内容哈希当成唯一 ID。
4. 显式记录点来源：原始保留点、原始水候选、生成水面点。不能仅凭文件名含 `_water` 判断，新水面也会追加进普通叶文件。
5. 干净输入与修复输出分开；若存在硬链接，改写前打断共享关系，避免间接修改输入。
6. 修改最细层后复用正常的叶节点和清单写入逻辑，不能删除记录后不更新文件头与元数据。

此前空叶兼容处理需要保留：有效点数为 0 时仍写可加载的透明填充页，读取时排除填充点，防止再次出现无法调度精细层的问题。[现有处理](D:/user/Desktop/code2/ai3d-waterpost/src/waterpost/lod.cpp:478)

### 7.4 并行执行与块边界

后续实现可以继续按块调度。需要渲染验证的阶段采用一张 GPU 对应一个进程；连通分析等 CPU 工作在各进程内控制线程与内存。

块边界判断读取必要的邻块最细层上下文，每个进程只写自己拥有的记录。跨块候选使用稳定标识合并，防止同一簇被重复删除或因截断产生不同判断。

邻域需要多大取决于连接半径和主体搜索范围。固定窄带只足够判断近邻连接，不一定足够计算跨很多块的完整簇；这类情况应合并跨块连通关系，或明确保留为未决候选。

## 9. 验证与验收方案

### 9.1 样本组成

| 样本 | 检查目标 |
| --- | --- |
| 已定位的 6 个独立簇 | 能解释原规则为什么保留；修复目标是已确认错误记录 |
| 一处树木 / 岸边粘连旧水点 | 错误点删除，连接的真实物体保留 |
| 一处建筑 / 桥墩附近水点 | 检查真实非水结构保护能力 |
| 正常树冠、细枝、电线等 | 检查误删，尤其是小簇和细连接 |
| 岸线与狭窄水道 | 检查水面覆盖、岸线退缩和裂缝 |
| 跨块结构 | 检查单块与多块处理一致性 |
| 新水面边界样本，仅当 C 成立 | 缩小或拆分后不再明显越界，且水面连续 |

除第一项外，当前文档没有声称已完成这些实测。验证视角应覆盖原反馈视角、邻近移动视角和俯视角；测试时确认查看的是最细层或明确选定的叶文件，避免无法比较。

### 9.2 必要的算法和文件检查

后续代码改动应增加针对真实失效机制的检查：

- 36～72 点的独立错误簇可以进入新候选流程，而同规模的真实物体有保留依据。
- 错误水点通过少量连接附着真实物体时，不能触发整簇删除。
- 真实桥梁、树干投影落在水掩码上，但有可靠遮挡和非水证据时应保留。
- 未观察、低置信度与强反证要得到不同决策，不能把未知当作错误。
- 跨叶、跨块、重复记录和并行处理的结果一致。
- 新水面尺度受限时，能处理覆盖不足与局部重采样，避免边界裂缝。
- 清理后的空叶仍可加载，填充点不参与连通簇和数量统计。

### 9.3 记录的指标

| 指标 | 统计方式 |
| --- | --- |
| 已确认错误点残留 | 对标注点逐记录检查，例如本案例的 313 条记录 |
| 真实结构误删 | 对保护样本计数，并检查多视角连续性 |
| 粘连改善 | 固定相机下对照，结合点级归属，不仅看单张截图 |
| 水面质量 | 覆盖不足、裂缝、越界和与物体的相交情况 |
| 数据完整性 | 输出可读、清单可达、文件头 / 点数 / 包围盒一致、输入未变 |
| 处理范围 | 粗层 BIN 摘要不变，未涉及的最细层记录按方案保持一致 |
| 工程代价 | 算法耗时、CPU 内存、GPU 显存、按块吞吐；下载和人工查看另计 |

对仅删除已确认 313 点的局部修复，验收应检查这些记录全部不再出现、删除清单外的有效记录未被改变，并复看对应画面。通用算法的全场误删率、召回率和耗时，需要完成标注与实验后报告，当前不填入估计值。

## 10. 建议的实施顺序

1. **补齐粘连样本定位。** 判明是旧水点残留还是新水面覆盖，并导出目前每个关键条件的结果。
2. **完成已确认样本的局部方案。** 对 6 个独立簇采用精确删除清单或新候选规则验证，先验证最小范围的结果。
3. **完善逐点水体判定。** 优先修复具体样本暴露的证据或保护问题，保持真实物体保护。
4. **扩展独立簇判断。** 加入主体关系与独立观测，利用真实小物体样本约束误删。
5. **有证据时处理新水面边界。** 在 C 类样本成立后修复尺度与足迹问题，不把它预先当成已确认根因。
6. **再扩大运行范围。** 局部和邻块验收通过后，对其他分块应用同一套版本化规则，保留决策记录与回退路径。

本次文档工作未修改算法、未重新运行补水，也未清理远端 LOD。后续实施范围应以已验证的问题和对应方案为准。
